# リアルタイムチャット 要件定義書（docs/chat/02_requirements.md）

- 根拠：docs/chat/01_request.md（WISH-CHAT-001〜005、講師配布）、授業テキスト「20261125リアルタイムチャット」
- 作業ブランチ：feature/chat

## 1 目的・利用者・範囲

### 1.1 目的
既存の TOP・TODO・AI 質問アプリに、利用者同士がリアルタイムで会話できる /chat を追加する。ブラウザから送ったコメントが、サーバーで検証・保存され、同じルームの参加者へ配信される流れを実装し、説明できるようにする。AI による自動応答は扱わない。

### 1.2 利用者
本アプリの一般ユーザーと管理者。ログイン機能はなく、ユーザー名は画面表示用の入力値として扱う（本人確認はしない）。

### 1.3 対象範囲
- /chat 画面（EJS）、Socket.IO による入室・投稿・配信、Neon への保存と最新 20 件の履歴
- 1 ルーム最大 5 名の定員制限（複数インスタンスでも合計で守る）
- 複数インスタンス間の新着の同期
- 入力検証とエラー表示

### 1.4 対象外
ログイン・権限管理、投稿の編集・削除、既読表示、入力中表示、複数ルームの作成・選択、AI 応答、画像やファイルの送信。

### 1.5 既存機能との関係
既存の /、/api/db-check、/todo・/todo-v2 と各 API、/ai・/ai/v2 と各 API、404、エラー処理は変更しない。HTTP サーバーの起動方法だけは、Socket.IO を同じサーバーに組み込むために変更する（同じポートで二重に待機しないこと）。

## 2 要件一覧

| REQ | WISH | 要件 | 受入条件（観察できる形） |
| --- | --- | --- | --- |
| REQ-CHAT-001 | 001 | GET /chat で EJS のチャット画面を表示する。ユーザー名とコメントの入力欄、送信ボタン、接続状態、履歴欄を持つ | /chat を開くと画面が表示され、接続状態が「接続中」から「入室済み」に変わる |
| REQ-CHAT-002 | 002 | 入室済みの参加者が送った投稿を、サーバーで検証・保存した後、同じルームの全参加者（送信者を含む）へ配信する | タブ A・B を開き、A から送ると A・B に同じ投稿が 1 件ずつ表示される。B から送っても同様 |
| REQ-CHAT-003 | 002 | 投稿（ユーザー名、コメント、作成日時）を DB に保存する。保存に成功した投稿だけを配信する | 1 回の送信で DB に 1 行だけ保存される。保存に失敗した場合は誰にも配信されない |
| REQ-CHAT-004 | 002 | 入室時と再接続時に、ルームの最新 20 件を古い順（上が古く下が新しい）に表示する | 21 件以上ある状態で開くと最新 20 件だけが古い順に表示される。再読み込み・再接続後も同じ |
| REQ-CHAT-005 | 002 | 履歴の取得中に届いた新着と履歴を投稿 ID でまとめ、同じ投稿を二重に表示しない | 接続を繰り返しても、同じ投稿は 1 件だけ表示される |
| REQ-CHAT-006 | 004 | 1 ルームの参加は最大 5 接続とし、6 接続目は入室を拒否する | 5 接続が入室済みのとき、6 接続目の画面に満席案内が出て、履歴の閲覧・新着の受信・投稿ができない |
| REQ-CHAT-007 | 004 | 切断・タブを閉じた接続の席を解放し、満席の画面から再試行で入室できる | 5 接続中に 1 つ閉じ、満席だった画面で「再試行」を押すと入室できる |
| REQ-CHAT-008 | 004 | サーバーの異常終了などで解放されなかった席も、一定時間後に回収する | 席の最終確認時刻から 60 秒を過ぎた席は数えない |
| REQ-CHAT-009 | 003 | 複数インスタンスで動かしても、同じルームの参加者全員に新着が届く | 2 つのプロセスに別々に接続した A・B の間で、双方向に投稿が届く（DB 同期による遅れは最大数秒） |
| REQ-CHAT-010 | 003・004 | 複数インスタンス合計で 1 ルーム 5 接続を守る | 2 台合計 4 接続の状態から両台で同時に入室すると、成功は 1 件だけで合計 5 接続になる |
| REQ-CHAT-011 | 005 | 入力を検証する。ユーザー名 1〜20 文字、コメント 1〜500 文字（前後の空白を除いた Unicode コードポイント数）。文字列以外、空文字、空白のみ、上限超過は保存・配信しない | 各不正入力で投稿者の画面に理由が表示され、DB に保存されず、他の参加者に届かない |
| REQ-CHAT-012 | 005 | 切断中は送信できない。再接続後は自動で再入室し、最新 20 件を取り直す | 通信を切ると送信ボタンが無効になり「再接続中」と表示される。復帰後、切断中に他の人が投稿した内容が履歴に表示される |
| REQ-CHAT-013 | 005 | DB 障害・通信失敗・保存失敗を、内部情報を含まない案内で表示し、サーバーは停止しない | 各失敗で画面に案内が出る。応答・画面に SQL や接続文字列が出ない |
| REQ-CHAT-014 | 非機能 | ユーザー名・コメントを文字列として表示する（EJS は <%= %>、ブラウザは textContent） | `<script>alert(1)</script>` を送ってもそのまま文字で表示され、実行されない |
| REQ-CHAT-015 | 非機能 | DB 接続情報などの秘密情報はサーバーの環境変数だけで扱い、ブラウザに出さない | public/chat、views/chat、ブラウザの通信に接続情報がない |
| REQ-CHAT-016 | 非機能 | 既存の TOP・TODO・AI 質問・404・エラー処理を壊さない | 既存の主要操作と存在しない URL の 404 が従来どおり |

## 3 確認する環境
| 条件 | ローカル（1 台） | ローカル（2 台） |
| --- | --- | --- |
| 方法 | npm run dev（ポート 3000） | 同じ .env で 2 プロセスを別ポート（3000・3001）で起動 |
| 確認する要件 | REQ-CHAT-001〜008、011〜016 | REQ-CHAT-009、010 |

Vercel（Preview・Production）での動作は、Functions の実行時間上限（Hobby は 300 秒）で接続が切れること、複数インスタンスに振り分けられることを前提に、再接続と DB 同期で補う。公開環境での確認内容は設計・テストで決める（要確認）。

## 4 要望書にない項目の決定・要確認
| 項目 | 決定（候補） | 理由・確認事項 |
| --- | --- | --- |
| 文字数上限 | ユーザー名 20、コメント 500 | 画面で読みやすい長さ。講師の指定があれば合わせる（要確認） |
| 参加人数の数え方 | Socket の接続単位（同じ人の 2 タブは 2 席） | テストを「6 つの独立した接続」で行うため。同じ人が 2 タブで入ると 2 席になることをテストで記録する |
| ルーム数 | 1 ルーム（default）。DB にはルーム ID 列を持たせる | 要望書の範囲。将来の複数ルームに備える |
| 満席時の再試行 | 画面の「再試行」ボタンで手動。自動では繰り返さない | 無制限の再試行で DB に負荷をかけないため |
| 席の回収時間 | 最終確認から 60 秒 | 各サーバーが 20 秒ごとに自分の接続の席を更新する |
| 配置先 | 評価はローカル。Vercel では動作の可否を確認して記録 | Vercel Functions の WebSocket 対応と実行時間上限（要確認） |
